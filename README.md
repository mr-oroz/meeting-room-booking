# Бронирование переговорной

Тестовое задание Frontend Engineer: интерфейс бронирования переговорной комнаты на рабочий день 09:00–18:00.

- **Демо:** _ссылка на Vercel_
- **Стек:** React 19, TypeScript, Vite, TanStack Query, MSW (mock API), Vitest + Testing Library

## Запуск

Нужен Node.js 20+.

```bash
npm install
npm run dev       # http://localhost:5173
npm test          # 51 тест
npm run build     # проверка типов + сборка в dist/
npm run lint
```

Бэкенд не нужен: запросы к `/api/bookings` перехватывает mock API прямо в браузере. Данные сохраняются в `localStorage`, поэтому демо переживает перезагрузку страницы. Кнопка «Сбросить демо-данные» внизу страницы возвращает исходные брони.

Подключить настоящий API:

```bash
VITE_USE_MOCKS=false VITE_API_URL=https://api.example.com npm run build
```

## Что сделано

**Сценарии:** выбор даты (стрелки, календарь, «Сегодня»), просмотр броней дня, создание, редактирование и удаление брони.

**Отображение — таймлайн дня.** День разбит на отрезки: брони, свободное время и прошедшее время. Высота отрезка пропорциональна длительности. Клик по свободному отрезку открывает форму с этим временем, клик по брони — редактирование. Форма по умолчанию предлагает первый свободный интервал, поэтому не открывается сразу с конфликтом.

**Бизнес-правила** — `src/domain/rules.ts`, чистые функции без React. Один и тот же модуль использует форма (мгновенная подсказка) и mock-сервер (окончательная проверка):

| # | Правило | Как сделано |
|---|---|---|
| 1 | В пределах 09:00–18:00 | Списки времени ограничены рабочим днём, сервер проверяет ещё раз |
| 2 | start < end | Варианты окончания всегда позже начала |
| 3–4 | От 30 минут до 2 часов | Окончание выбирается только из допустимых вариантов |
| 5 | Без пересечений, касание допустимо | `overlaps()`: `a.start < b.end && b.start < a.end` |
| 6 | Нельзя в прошлое | На сегодня прошедшее время недоступно (до шага 15 мин). Для прошлой даты форма закрыта |
| 7 | Редактирование не конфликтует само с собой | Проверка пересечений исключает `id` редактируемой брони |
| 8 | Конфликт с сервера | См. ниже |

**Конфликт с сервера (правило 8).** Сервер отвечает `409`, даже если интерфейс считал слот свободным. В этом случае:
- показывается понятное сообщение «Время только что заняли»;
- список броней перезапрашивается, и видно, кто занял время;
- всё, что ввёл пользователь, остаётся в форме, и она сразу подсказывает новое пересечение.

Чтобы это можно было проверить без второго пользователя, в демо-панели внизу есть переключатель «Следующее сохранение получит конфликт 409». Mock-сервер перед сохранением сам создаёт пересекающуюся бронь «другого сотрудника».

**Состояния интерфейса:**
- загрузка (скелетон);
- пустой день;
- ошибка загрузки с кнопкой «Повторить»;
- фоновое обновление («Обновление…»);
- отправка формы (кнопки заблокированы, «Сохранение…»);
- ошибки сервера (`409`, `422`, `404`, `500`, нет сети);
- подтверждение удаления.

Медленную сеть и ошибку `500` тоже можно включить в демо-панели.

**Слой API отделён от UI:**
- `src/api/bookingsApi.ts` — интерфейс `BookingsApi` и его HTTP-реализация по контракту из задания;
- `src/api/http.ts` — `fetch`, разбор ошибок в `ApiError` (`status`, `code`, `conflictWith`);
- `src/features/bookings/queries.ts` — хуки TanStack Query.

Компоненты не знают ни про `fetch`, ни про mock: mock API перехватывает запросы на уровне сети (MSW). Поэтому переход на настоящий бэкенд — это переменные окружения, а не правки кода.

**Mock-сервер** (`src/mocks/handlers.ts`) валидирует всё сам:
- `400` — некорректный запрос;
- `404` — бронь не найдена;
- `409` — пересечение, с полем `conflictWith`;
- `422` — нарушение остальных правил, с кодом правила.

Если Service Worker недоступен (например, приватное окно Firefox), те же обработчики подключаются через обёртку над `fetch` (`src/mocks/fetchFallback.ts`).

**Доступность и адаптивность:**
- семантика: `section` с заголовками, список `ol`, у всех полей есть `label`;
- ошибки полей связаны с полями через `aria-describedby`, `aria-invalid`;
- `role="alert"` для ошибок, `aria-live` для статуса сохранения;
- видимый фокус. При выборе слота фокус переходит в форму;
- `prefers-reduced-motion` отключает анимацию скелетона;
- на узких экранах расписание и форма встают в колонку.

**Тесты (51):**
- правила — все границы: касание, ровно 30 мин и 2 ч, прошлое время, редактирование самой себя;
- mock API — коды ответов;
- интеграционные тесты страницы: создание, конфликт 409 с сохранением данных, валидация до отправки, редактирование и удаление, недоступность прошедшей даты, ошибка загрузки и повтор.

## Допущения

В задании это не уточнено, поэтому я выбрал так (в реальном проекте уточнил бы у команды):
- **Шаг времени — 15 минут.**
- **Часовой пояс — локальное время браузера.** Дата считается по местному календарю, не по UTC.
- **Начавшиеся и прошедшие брони только для просмотра.** Перенести такую бронь, не нарушив правило 6, нельзя. Досрочно освобождать комнату в задании не требовалось.
- **Одна переговорная, без пользователей.** Любую будущую бронь может изменить любой — авторизации по заданию нет.
- **Бронь редактируется в пределах своего дня.** Чтобы перенести её на другую дату, нужно удалить и создать заново.

## Что не сделано / что бы доделал

- Переключение на разные переговорные и владельцы броней.
- Выбор времени перетаскиванием по таймлайну.
- Оптимистичное обновление списка. Сейчас список перезапрашивается после каждого изменения: проще и надёжнее при конфликтах.
- E2E-тесты в настоящем браузере (Playwright) и проверка доступности через axe.
